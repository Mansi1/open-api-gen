## Goal
CLI + library `open-api-gen`: one OpenAPI 3.0.x | 3.1.x | 3.2.x document (JSON|YAML) + optional config → output DIRECTORY shaped like `../st-open-api/dist3` (reference output, see "Output layout"), plus opt-in runtime validation + transformation.
- generated code has zero runtime deps EXCEPT user-hook modules the config names.

## Output layout (target := `../st-open-api/dist3`, st-open-api 1.4.0 on `examples/SpaceTraders.json`)
VERIFIED BC read of `dist3/` (199 files):
```
<out>/
  version.json                       # generator version, timestamp, source path, effective config
  open-api.json, open-api.yaml       # input doc (after overlay/filter) in both formats
  interface/components/<Schema>.ts   # one per components.schemas entry + per extracted inline enum/object
  interface/request/<OpId>Request.ts
  interface/response/<OpId>Response.ts (+ <OpId>Response<Prop…>.ts for nested inline objects)
  interface/parameter/<OpId>{Path,Query,Header,Cookie}Parameter.ts
  service/<tag-kebab>/<TagPascal>Service.ts   # one class per TAG (human rev 3; dist3 used first path segment)
```
Service grouping (human decision rev 3: by tag). VERIFIED tag usage BC `scratchpad/scripts/tags.mjs` over 7 `examples/`: 0 multi-tag ops; 2 untagged ops (SpaceTraders 1, unified-api 1); tag names with spaces/parens/dashes common (Jira `Issue custom field values (apps)`, milkscout `shipping-offer`). Rules:
- op → FIRST tag (multi-tag: first only, NEVER duplicated across classes).
- untagged → `DefaultService` in `service/default/`.
- tag → `TagPascal` = words split on non-alphanumerics, PascalCase (`Issue custom field values (apps)` → `IssueCustomFieldValuesAppsService`, folder `issue-custom-field-values-apps`); leading digit → `_` prefix; two tags mapping to one name → generation error naming both.
- top-level `tags[].description` → class doc comment.
Per-file conventions (VERIFIED from `dist3`, keep 1:1 unless marked NEW):
- header `/** This file was generated by <generator> */`; relative `import { X } from '../components/X'`.
- `export interface` per object schema; properties sorted alphabetically; optional = `?`; doc comment = description + `open-api validation:` list of constraints (`minLength`, `minimum`, ...); type-level doc comment embeds the original schema JSON.
- enums → `export type X = 'A' | 'B'` + `export const XValues: Array<X> = [...]`; inline enums extracted to own file named `<Parent><Prop>`.
- service: `export class <Segment>Service { constructor(public config: { send: <T = void>(request: { method; url; queryParameter?; urlParameter?; headerParameter?; cookieParameter?; body? }) => Promise<T> }) }`; one arrow-fn method per op named camelCase `operationId`; args order `(urlParameter?, queryParameter?, headerParameter?, body?)` typed by the parameter/request interfaces; `url` = templated path (`/systems/{systemSymbol}`), NOT interpolated; `send` owns HTTP; `headerParameter` includes `accept`/`content-type` from spec.
- NEW (fixes vs dist3): types typed with `unknown` NOT `any` in `send` contract; method doc comments use `/** */` (dist3 uses `/*`, invisible to IDEs); `send` contract exported once from `service/Send.ts` instead of repeated inline per class.
- NEW `service/fetchSend.ts`: default `createFetchSend({ baseUrl, fetch?, headers? })` implementing the `send` contract (path interpolation with `encodeURIComponent`, query/header/cookie serialization, body encoding, non-2xx → `ApiError`). dist3 left this to every consumer. Optional to use.
- NEW validation/transform (rev 2 scope) lives in service methods, see DECISION.

Human-chosen scope (rev 2, AskUserQuestion answers):
- validation: (V1) runtime **response** validation in generated client; (V2) **input spec** validation in generator. NOT request validation.
- transformation: (T1) format → JS types; (T2) naming transforms; (T3) user-defined hooks; (T4) spec transforms (filter + overlay).
- runtime validation + transform = **opt-in per client** (`validate: true`, `transform: true`); code always emitted.

Out of scope (v1): Swagger 2.0 (clear error), webhooks/callbacks, external file|URL `$ref` (clear error), request validation, auth helpers beyond `headers`, JS (non-TS) output (dist3 `language` option).

## DECISION
- Two stages, joined ONLY by the internal format (human rev 5: "transform it to an internal format and then create the client"):
  - Stage 1 `src/intermediate-format/`: `load → overlay → validateSpec → filter+prune → normalize → planTransforms → buildIntermediateFormat`: OpenAPI doc + config → `IntermediateFormat`.
  - Stage 2 `src/emit/`: `intermediate format → Files`. Stage 2 NEVER sees the OpenAPI doc, `$ref`s, version, or config.
  Overlay before validation BC the generated-from doc is what must be valid; filter after BC it only removes.
- `IntermediateFormat` (`src/intermediate-format/types.ts`) = plain JSON data (NO functions, classes, Maps, cycles; refs by name), versioned `intermediateFormatVersion: 1`, fully resolved: every decision Stage 2 needs is already made: final TS names, file paths, service class per op, App vs Wire types, codec per node, constraints for validators, content types, param styles. `src/intermediate-format/normalize.ts` alone knows 3.0|3.1|3.2 differences.
- intermediate format is inspectable: CLI `--emit-intermediate-format <file.json>` writes it; library exports `buildIntermediateFormat(config)` + `emit(intermediateFormat)` so users MAY transform the intermediate format between stages (e.g. rename); stable contract, documented.
- Contract checks: (a) `src/intermediate-format/intermediate-format.schema.json` (JSON Schema draft-07, the format ts-json-schema-generator 2.9.0 emits) generated from `src/intermediate-format/types.ts` is the intermediate format contract; EVERY `buildIntermediateFormat` output in tests validates against it (hyperjump); (b) `test/boundaries.test.ts` asserts no file under `src/emit/` imports from `src/intermediate-format/` except `src/intermediate-format/types.ts` (import-graph scan), so Stage 2 cannot re-derive Stage 1 state; (c) `JSON.parse(JSON.stringify(intermediateFormat))` deep-equals `intermediateFormat` (pure data).
- Generated client data flow per response: `text → parse (lossless reviver IF any int64→bigint) → validate(Wire schema) IF validate → decode(Wire→App) IF transform → return`. Per request: `App → encode(App→Wire) IF transform → serialize`. Validation ALWAYS against wire shape BC spec schemas describe the wire.
- Where it runs: service method → `config.send` returns raw wire body → IF `config.validate` THEN `validate<Name>` (from `interface/**/<Name>.validate.ts`) → IF `config.transform` THEN `decode<Name>`. Service config grows `{ send, validate?, transform? }` (backward compatible with dist3 `{ send }`).
- Types follow runtime: `interface/` = wire types exactly as dist3; IF a schema has ≥1 codec THEN `interface/app/<Name>.ts` holds its App type (others: App = Wire, no file). Service class generic `class XService<M extends "wire" | "app" = "wire">`; config `transform: M extends "app" ? true : false|undefined`; return type `M extends "app" ? App.X : X`. Proof = `@ts-expect-error` assignability tests, NOT just compiling.
- Co-location: validators + codecs emitted next to their type (`<Name>.validate.ts`, `<Name>.codec.ts`) ONLY for schemas used in responses|requests, so unused ones tree-shake.
- Interface naming follows dist3 (owner: `src/names.ts:interfaceName`); service grouping by tag (owner: `src/layout.ts:serviceOf`); deviations from dist3 approved by human (rev 3); name collision across sources (e.g. component `GetShipResponse` vs derived response name) → suffix `_1` + warning.
- Config: `open-api-gen.config.json` (JSON BC hook refs are module specifiers, no code needed) + CLI flags overriding it.

## Config contract (`src/config.ts`, the ONE owner; validated at load, unknown keys = error)
```ts
type Config = {
  input: string; output: string;
  validateSpec?: boolean;                // V2, default true; false = escape hatch for slightly invalid real specs
  overlay?: string | string[];           // T4
  filter?: { tags?: string[]; excludeTags?: string[]; operationIds?: string[] }; // T4
  naming?: { properties?: "preserve" | "camelCase" };                        // T2, default preserve
  formats?: { "date-time"?: "Date" | "string"; date?: "Date" | "string"; int64?: "bigint" | "number" }; // T1; defaults Date, Date, bigint (rev 4)
  transformers?: Record<string, { type: string; import: string; decode: string; encode: string }>;
  // T3 key: "format:<name>" | "schema:<ComponentName>"; type = TS type name exported by `import`
};
```
